# Listening audio generation data design

## Scope

Teacher-owned IELTS Listening drafts may generate an audio preview from the
section transcript. A dedicated Node.js worker thread runs the pinned Kokoro
model through `kokoro-js`, encodes the generated samples as WAV, and returns the
bytes to the API for storage in the existing private object store. Keeping CPU
inference and WAV encoding off the API event loop allows unrelated Student and
Admin requests to continue while generation runs. The Teacher must listen to
and confirm the preview before the normal section save attaches it.

## Persistence

No new table or migration is required.

- `media_objects` stores each generated WAV with `media_type = AUDIO`,
  `source = SYSTEM_GENERATED`, `visibility = DOMAIN_AUTHORIZED`, and the
  existing checksum, duration, size, and object-storage fields.
- `test_sections.media_object_id` points at the confirmed generated recording
  only after the normal section save.
- The primary-language `test_section_translations.content` field stores the
  transcript only through that same save.
- `audit_logs` records `LISTENING_AUDIO_GENERATED`, including the previous and
  replacement media object identifiers.

Regeneration creates a new immutable owner-only media preview without changing
the draft. Saving a confirmed preview promotes it to domain-authorized media and
changes the draft section reference. Previously generated objects are retained
so an audit trail is not destroyed by replacement.

## Ownership and lifecycle

Generation is allowed only when all of these conditions are true:

1. the authenticated member is a Teacher;
2. the section belongs to a group owned by that Teacher;
3. the version is an active `DRAFT`;
4. the test skill is `LISTENING`; and
5. the transcript is non-empty and within the configured length limit.

The media row is created in `VERIFYING` before bytes are written. A successful
write and a final ownership/draft check promote the preview object to `READY`.
A provider, validation, storage, or concurrent state failure marks the object
`REJECTED` and never changes the section. The existing `updateTestSection`
ownership check attaches a confirmed preview during save.

## Trust boundary

The samples are generated by the pinned local `kokoro-js` library, not uploaded
by a user. The API encodes mono PCM16 WAV, enforces the object-store size and
duration limits, and computes SHA-256 before storage. Because this is trusted
generator output, the object is recorded as clean with the generator identity instead of being
routed through the user-upload malware scanner.

## API contract

`generateListeningAudio(input: GenerateListeningAudioInput!)` accepts the
target `testSectionId` and transcript and returns the generated media identifier,
duration, and short-lived private preview URL. The mutation remains synchronous
from the Teacher client's perspective, while its CPU work runs outside the API
event loop. Published versions remain immutable; the client creates the next
draft version before invoking generation.

## Configuration

The API reads:

- `TTS_DEFAULT_VOICE`
- `TTS_MODEL_ID`
- `TTS_MODEL_DTYPE`
- `TTS_MAX_TRANSCRIPT_CHARACTERS`

The API pins `kokoro-js` `1.2.1`. On first use, Transformers.js downloads the
configured model from Hugging Face and caches it locally. Each API process owns
one lazy, persistent TTS worker thread. That worker keeps one loaded model and
serializes CPU generation requests. Worker failure rejects the active request;
the next request starts a fresh worker without restarting the API process.
